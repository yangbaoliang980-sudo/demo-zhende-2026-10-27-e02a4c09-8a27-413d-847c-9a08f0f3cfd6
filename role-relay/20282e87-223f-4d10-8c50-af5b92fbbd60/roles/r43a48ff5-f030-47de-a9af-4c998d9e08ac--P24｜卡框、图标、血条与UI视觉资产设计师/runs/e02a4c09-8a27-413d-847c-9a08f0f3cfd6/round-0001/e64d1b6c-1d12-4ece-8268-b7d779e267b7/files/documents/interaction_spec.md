# P23 逐态交互与输入规范

版本：P23-INTERACTION/0.1.0-proposal。适用 IC-21；表现边界关联 IC-23。本文是可实现的设计契约，状态行为未接入真实游戏。

## 一、权威与本地状态

P14 是战斗状态的唯一写入方。P15 给出合法性、费用及目标候选；P19 只展示并发送既有命令。UI 不扣费，不重算伤害，不替服务补目标，不按血量自行判终局。P29 演出不能打开输入、写钱包或补发命令。

UI 本地只持有选择、详情展开、焦点、行内确认和演出偏好。所选牌、预告、按钮按下反馈都不是领域提交成功。数值只在新权威视图到达后更新；等待状态不通过乐观改血、改费用制造“已成功”的印象。

输入保护按既有 owner 条件组合：没有合法快照 → 原操作待确认 → 连接/版本/存档保护 → 终局或非玩家阶段 → 必需卡牌上下文 → 普通选择。意图缺失独立显示，不额外修改 END_TURN 资格。状态条不能覆盖并遗失原请求身份。

## 二、手牌选择与目标确认

| 步骤 | 用户输入 | UI 变化 | 允许的业务命令 |
| --- | --- | --- | --- |
| 选择牌 | 单击 / Enter / Space / 手柄 Confirm | 明确“已选择”；展开完整效果；焦点保持在该实例 | 0 |
| 选目标 | 对合法目标确认；多目标逐个切换 | “可选目标 / 已选目标”文字加轮廓；摘要列全部对象 | 0 |
| 校验目标集 | 对照 P15 allowed_target_sets | 精确匹配后启用确认按钮；不自动补齐或改排序语义 | 0 |
| 确认出牌 | 显式激活“确认出牌” | 立即锁住新提交，保留原身份与原载荷 | 1 次 PLAY_CARD |
| 等待/未知 | 查询原操作 / 查看详情 | 持续提示；维持最后已确认状态 | 同 ID 原命令重发；不是新增逻辑出牌 |
| 接收结果 | P14 新快照/已提交事件 | 先绑定最终数值，再允许 P29 装饰性演出 | UI 不追加命令 |

无目标牌仍须最终确认。只有一个目标也不自动出牌。群体牌须显示作用范围并采用 owner 给出的合法集合；不能因为画面只有一个敌人就将全体效果改写为单体。死亡、移除、快照更新使原选择不合法时清除该本地选择、说明原因，焦点回到剩余同组实例或状态/标题，绝不切到另一个敌人后自动确认。

费用不足牌保持名称、费用和“当前不可用”的原因可读。若上游用 native disabled 按钮，另提供可聚焦的卡牌详情入口；不能把唯一解释放在 disabled 元素的 tooltip 中。禁用牌的“查看”不得走同一出牌 handler。

取消/空白单击只取消本地选中，是否清空目标依 P19 既有选择规则；Esc 逐层返回：详情 → 目标 → 卡牌 → 行内确认。Esc 不撤销已提交的战斗命令，不承担 Anki Undo。

## 三、结束回合

保持现有 END_TURN 语义及 P19 canEndTurn。卡牌上下文或意图未同步时，不能自行添加禁止结束回合的玩法规则。

本岗提议：显式激活“结束回合”后在同一操作区显示行内复核，保留敌方意图、未出牌提示、继续选择和确认结束。初始焦点在“继续选择”；只有第二次明确确认发送 END_TURN。该提案见 W06 / P23-RFC-003，批准前不要求 P19 改现有单次按钮行为，不增加领域枚举。行内复核不是模态框，Tab 仍可到战场详情；快照或资格变化时复核失效并说明。

不新增跳过回合的资源奖励、惩罚、长按计时、自动结束或“有费用就不能结束”的规则。

## 四、重复输入、等待与恢复

一次按下—释放只对应一次激活。忽略 key repeat；按键持续按住时发生焦点移动，必须等释放后再接受新的确认。双击、鼠标释放与键盘同时发生、手柄热插拔、窗口恢复都不能再次提交。派发前同步进入 busy，不能等网络返回才禁用。

同一操作沿用原 request/command identity 与原载荷。P02 的重复命令检查与 revision 判断次序由领域契约决定，UI 不通过换新 ID 绕过。结果未知保留查询入口；超时只改变提示，不认定成功、失败或允许重来。

P21 已提供隔离 SQLite 的查询和一致读能力；本轮不把它记成“完全未交付”。尚缺的是 P20 外层意图与领域事务的受理映射、正式 gateway、能力接受和真实证据。P20 现有接口拒绝 durable=true，不能直接替换类名或把 boolean 改为 true。即便查询得到 ABSENT，也须遵守被受理的恢复协议，不能一概转换为新请求。

### 战斗查证与元系统只读查询必须分开

P19-API 的“查询本次操作”在当前版本中调用 retryPending → sendPending，**重发同一 command_id、expected_revision 和 payload 的完整原命令**。这不是只读请求；若原命令此前未执行，该重发可能完成原来已获玩家确认的操作。核心负责防止同一逻辑命令被应用两次。验收要区分 transport send count 与 distinct command_id / logical apply count，不能要求重试场景网络发送次数仍为 1。

P19 当前 pending 仅在内存。返回前台会同步快照，但完整页面重载不能恢复未决命令。正式恢复端口、持久去重保留期和身份连续性须 P13/P14/P21 确认；不能将本包 W03 当作重启恢复已实现的证明。没有原身份时不允许 P23 自行生成替代请求。

P20 的原意图 lookup 与学习记录 refresh 保持其各自只读查询契约；P20 正式 gateway 尚待受理。一个“查询”中文按钮名不能推导相同网络语义。`ux_anchor_contract.json/recovery` 分别明确这三类路径。

## 五、角色、编队、章节和奖励

- 三席按位置控制选择；角色身份按 character_id 跟随。选中已占用角色仅交换本地草稿，仍需明确保存。保存前后两种顺序不能混写为一个“当前阵容”。
- 养成：资格、费用、当前等级与钱包使用同一可核验视图。升级框默认取消；焦点限制在现有模态框中，Esc 关闭并回触发按钮；若触发对象消失则回所选角色或页标题。提交之后框可关闭但原操作待确认状态必须继续存在。
- 存档不可变更时，升级、保存编队、出战、领取沿用上游保护。按钮旁写“恢复待核对，暂不能出发”等具体原因，不能同时以醒目的 READY 暗示允许提交。
- 奖励：胜利与领取分别呈现。领取未知后保留原操作查询，禁止创建另一笔领取。展示当前已确认余额，不把候选奖励额加进钱包。
- 连接：Anki 未连接、游戏内部服务断连、存档待恢复是不同原因。不同 owner 的状态不能合并为一个红点。

## 六、键盘、手柄与鼠标的焦点契约

`keyboard_focus_matrix.tsv` 给出顺序、组内方向、激活、取消、鼠标等价和失效恢复。`focus_graph.json` 的闭环边只供游戏内方向焦点使用，不要求截获浏览器级 Tab。元界面组合顺序为全局导航 → 全局只读工具 → 当前页面局部；模态升级框暂时取代这个顺序。

重复列表用稳定实例键保留焦点。手牌重排后，同一 card_instance_id 仍代表同一焦点，不以位置或译名定位。动态锚点模板必须展开，静态控件必须一物一 ID。header/status 在异常时允许程序聚焦，不因此加入每次 Tab 顺序。

焦点采用至少 3px 外轮廓及形状/选中标记，不依靠色相差。鼠标 hover 不转移键盘焦点；只用鼠标点击也能完成选牌、选目标、确认、结束和查询，无必须拖拽、悬停或按住的核心动作。焦点必须滚动到可见区域且不被底栏/横幅遮住。

手柄使用逻辑 Confirm / Back / Direction，南键确认、东键返回仅为未冻结平台的候选。屏幕按实际映射显示图标和文字，不提前承诺某一厂商键位。摇杆不是唯一导航方式，D-pad 可完成流程；断连不确认、不取消领域请求，切回键盘继续。真机、固件、辅助控制器测试 NOT_RUN。

## 七、反馈与播报

操作结果用持久正文或记录保留。仅信息更新不抢焦点；每个已提交批次合并为一条简短播报，不逐帧播报数字或每个粒子。结果未知、安全相关失败和资格变化必须可再次查看。屏幕阅读器应获得名称、角色、状态、描述关系；焦点不会落入装饰层。实际引擎无障碍树需 P19/P20/P34 接入并由 P33/P39 另测。
